# 踩過的坑

每一條都是這次真的發生過的事。依類別分組，格式是「症狀 → 原因 → 解法」。日期是 2026 年 9 月。

## 一、Windows 端（兩種方法都可能碰到）

| # | 症狀 | 原因 | 解法 |
|---|---|---|---|
| 1 | 9/16 06:22 藍屏 0x50（PAGE_FAULT_IN_NONPAGED_AREA） | 某一版程式在讀取卡住時用 `pnputil /restart-device` 重啟 USB 裝置，把正在 I/O 的裝置拆掉 | **永遠不做 USB 重置**。卡死一律停下來，請人拔電源 |
| 2 | 沒有任何程式在跑，USB 仍每 16 秒重置一次 | Windows 的 Spot Verifier、NTFS 自動修復、Chkdsk 背景掃描在反覆讀損毀的 MFT；「修復」目錄時還可能刪掉項目 | 接硬碟前以系統管理員執行 `scripts/準備硬碟.bat`；不用的時候拔掉硬碟 |
| 3 | `taskkill` 之後，程式還要 15～45 分鐘才真的消失 | 主執行緒卡在核心的讀取裡，要等 Windows 放棄那次讀取 | 用小幫手程序等它真的消失再重啟，不要以為 kill 了就結束了 |
| 4 | 硬碟卡死時，每個資料夾都被記成「讀不到」 | 分不出「資料夾壞了」和「整顆硬碟卡死」 | 失敗時用不經快取的方式讀一個確定完好的檔案當探測，讀不到就是硬碟卡死，撤銷這段期間的紀錄 |
| 5 | Google Drive 鎖檔被記成壞軌，還觸發「連續 5 張失敗」把整個資料夾延後 | 來源讀取錯誤和目的地寫入錯誤混在一起算 | 兩種錯誤分開處理，寫入失敗等 60 秒重試 |
| 6 | 「磁碟已滿就暫停」從來沒生效 | 只判斷 Windows 錯誤碼 112，但 Python 回報的是 errno 28 | 兩種都判斷 |
| 7 | 用系統管理員執行 bat，整片「'xxx' 不是內部或外部命令」 | bat 檔用 LF 換行、內容有中文，cmd 用系統碼頁（cp950）讀，把每一行切碎 | **bat 內容一律純 ASCII + CRLF**；中文路徑放進程式的常數或 ps1 |
| 8 | PowerShell 算網段遮罩算錯 | Windows PowerShell 5.1 把 `0xFFFFFFFF` 讀成 -1 | 用 `[uint64]4294967295`；交給使用者前先離線驗算 |
| 9 | ps1 裡的中文字變亂碼 | Windows PowerShell 5.1 用系統碼頁讀沒有 BOM 的 .ps1 | ps1 內容保持純 ASCII |
| 10 | AI 工具啟動的程式沒有真的在跑，或對話一結束就被收掉 | AI 工具用 `Start-Process` 開的視窗不一定真的執行；在 AI 的 shell 裡跑，逾時或對話結束會被一起關掉 | 用檔案總管或工作排程器啟動（方法一），或用 `start_background.ps1` 脫離啟動（方法二）；啟動後用鎖定檔與日誌確認 |
| 11 | 程式改了卻好像還在跑舊版，雲端上的版本和手邊的不一致 | 程式放在 Google Drive，背景同步可能覆寫；改完還要手動複製到 repo | 程式只放本機 git repo，雲端硬碟只放產出 |
| 12 | G 槽顯示只剩 516 GB，但雲端空間有 5 TB | Google Drive 串流模式顯示的是本機暫存碟的空間 | 寫入太快就暫停，等上傳釋出暫存空間；電腦不睡眠、同步不暫停 |
| 13 | 用檔案總管整個資料夾複製，結果 0 位元組 | 碰到讀不出來的檔案，整個複製工作停住 | 故障碟不要用檔案總管複製，也不要用檔案總管打開（產生縮圖會讀每一張照片） |
| 14 | 硬碟掉回 Windows 後，直接讀檔每個都 `[Errno 22] Invalid argument` | 硬碟在 Windows 的驅動下已經讀不動 | 硬碟一旦讓 Windows 出問題，就不要再從 Windows 讀，回到方法二 |

## 二、VMware 與 USB

| # | 症狀 | 原因 | 解法 |
|---|---|---|---|
| 15 | 硬碟一接上就掉回 Windows，接著 UAS 每 16 秒重置（又差點凍機） | vmx 的 `usb.autoConnect.device0` 讓同一顆硬碟觸發兩次連線，第二次失敗把第一次撤銷 | 不用 autoConnect，`usb.generic.autoconnect = "FALSE"`，每次手動在 VMware 選單 Connect |
| 16 | 虛擬機開機 3～5 分鐘後整個凍結，畫面不動、SSH 全逾時 | vmx 裡殘留 `usb_xhci:6`、`usb_xhci:7` 舊集線器項目 | 刪掉這些項目（之後穩定性測試 18/18 次通過）。虛擬機又凍結時先檢查 vmx |
| 17 | 硬碟在虛擬機裡完全讀不到，第一個讀取指令就 30 秒逾時，連容量都讀不出來 | 接在 USB 3.0 埠，Linux 用 `uas` 驅動，這顆碟在 UAS 下不能用 | **接 USB 2.0 埠**（黑色），改走 `usb-storage`。沒有 USB 2.0 埠就中間接一個 USB 2.0 集線器 |
| 18 | `/dev/disk/by-id/` 連結永遠不出現，整個救援無法開始 | `amd64_edac` 模組在 VMware 裡存取不存在的晶片組暫存器而崩潰，連帶讓處理硬碟的 udev-worker 死掉 | 開機參數加 `modprobe.blacklist=amd64_edac`，之後開機完全乾淨 |
| 19 | 接上硬碟後 vm-check 或 mft 一直卡著 | 這顆碟通電後要 7 分鐘才就緒（Not Ready / becoming ready），Linux 預設 30 秒逾時會提早重置它 | 程式自動把 SCSI 逾時設成 180 秒；這段時間是正常等待，不是當掉 |
| 20 | 拔插電源後硬碟沒回到虛擬機 | 關掉 autoConnect 之後，重新上電的硬碟預設留在 Windows | 每次拔插都要在 VMware 選單點 Connect |
| 21 | 虛擬機配 4 GB 記憶體 | 高估了需求 | SystemRescue 跑 ddrescue 實測只用 379 MB，1.5 GB 就夠，省下來給 Windows 的檔案快取 |

## 三、ddrescue

| # | 症狀 | 原因 | 解法 |
|---|---|---|---|
| 22 | 範圍內明明是好資料卻沒讀，一直留在「待修剪」 | ddrescue 1.30 搭配 `--domain-mapfile` 時，`-c 256`（一次 1 MiB）會漏讀，`-c 64` 也會 | 用 `-c 16`（演練時 `-c 16`、`-c 32` 和預設值都正確） |
| 23 | 補讀時 ddrescue 不處理第一輪留下的區塊 | 限定範圍模式下，沒有 `-A` 不會回頭處理「待修剪／待刮取」 | 補讀用 `-A -r1` |
| 24 | 一批剛開始，回報連續 10 分鐘顯示 0% | ddrescue 依 mapfile 大小自動決定存檔間隔，6 MB 的 mapfile 要 10 分鐘才第一次存 | 加 `--mapfile-interval=60` |
| 25 | 硬碟卡死 2.5 小時，ddrescue 的 `-T 10m` 完全沒反應 | 程式被凍在不可中斷的 I/O 等待（D 狀態），連自己的計時器都跑不了 | 看門狗放在虛擬機外面的控制程式，看 mapfile 的讀取位置有沒有前進 |
| 26 | 該等的時候放棄，該叫人的時候空轉 | 把「硬碟卡住」和「硬碟掉線」當成同一件事 | 分開處理：裝置還在就等（最多 45 分鐘，常常會自己恢復）；裝置不見了立刻停下來叫人 |
| 27 | 讀到某些位置，整顆硬碟就鎖死 | 實體損傷集中在特定區域（這次五次鎖死都在 2245～2500 GB） | 記成危險區、自動跳過，最後才補讀；讀取順序改成**離危險區越遠的先讀** |
| 28 | 演練時 ddrescue 每 4 秒被重啟一次 | ddrescue 結束了但沒有任何進度，控制程式卻判斷「還沒讀完，繼續」 | 範圍內統計和上一輪完全一樣就停止，絕不自動重跑 |

## 四、稀疏映像檔與 SMB 共用

| # | 症狀 | 原因 | 解法 |
|---|---|---|---|
| 29 | 建一個「稀疏」映像檔，一分鐘吃掉 120 GB | Python 的 `truncate()` 在 Windows 上會真的寫零 | 先 `FSCTL_SET_SPARSE`，再用 `SetFilePointerEx` + `SetEndOfFile` 設大小 |
| 30 | 半小時吃掉 511 GB，C 槽只剩 69 GB | 映像檔被刪掉後，ddrescue 自己在 SMB 上建了一個普通檔案；寫到 2744 GB 的位置，NTFS 從 0 開始實際配置並填零 | 每次 `copy` 開始前都確認映像檔存在而且是稀疏檔 |
| 31 | ddrescue 回報 mapfile 錯誤 | Windows 剛寫好的 domain 檔，虛擬機透過 SMB 讀到快取的舊版本 | 啟動 ddrescue 前比對 SHA256，不一致就重試 |
| 32 | 一天 11,885 次「延遲寫入失敗」，記憶體的髒頁漲到 13.5 GB，釋放映像檔空間全數失敗 | 為了省空間不斷在稀疏映像檔上打洞，每打一個洞就多切出片段；累積到 1,929,562 個片段後撞上 NTFS 片段對應表的上限 | **只有空間不夠時才打洞**（可用空間 < 剩餘待救量 × 1.5 + 50 GB）。已經撞上限的話，先 `extract` 把讀到的資料輸出，再把映像檔整個刪掉重建 |
| 33 | 硬碟卡住或程式被強制結束時，寫入 flush 不出去 | SMB 預設 `cache=strict` 把寫入堆在客戶端快取 | 掛載加 `cache=none`（故障碟只有 5～25 MB/s，關快取不會變慢）。這**不是**第 32 條的解藥，兩件事要分開看 |
| 34 | 強制結束程式後出現延遲寫入失敗 | `Stop-Process -Force` 留下未完成的 SMB 寫入 | 先在虛擬機裡停 ddrescue，等它寫完 mapfile，再停 Windows 端 |
| 35 | mapfile 說讀到了，映像檔裡卻是空的 | 當機或延遲寫入失敗 | **只有輸出到目的地的資料才算數**：每批開始前，把「標記讀到但還沒輸出」的區段改回未讀重讀 |
| 36 | 重新規劃後輸出一堆全是 0 的檔案（差點發生） | 已輸出的資料在映像檔裡已經打洞歸還，但 mapfile 仍是「讀到了」 | 一旦開始輸出，程式拒絕重跑 `plan` |

## 五、NTFS 解析與檔案

| # | 症狀 | 原因 | 解法 |
|---|---|---|---|
| 37 | 解析 MFT 時當掉（NotYetRead） | 大檔案的屬性清單（`$ATTRIBUTE_LIST`）是非常駐的，存在 MFT 以外的位置，第一輪沒讀到 | 讀完 MFT 後收集這些位置補讀，再重新解析 |
| 38 | 有大小但沒有內容的檔案讓輸出當掉 | 稀疏檔（多半是沒下載完的 mp3），磁碟上根本沒有資料 | 標記成「原檔空白未存」 |
| 39 | 兩個檔案共用同一段磁區，其中一個輸出後另一個變成全 0 | 硬連結 | 共用磁區的檔案永遠不打洞 |
| 40 | 小檔案沒被輸出 | 資料直接存在 MFT 記錄裡（resident），不在一般磁區 | 輸出時直接從 MFT 記錄取資料 |
| 41 | 少數檔案寫不進 G 槽 | Google Drive 不接受檔名開頭是空格的檔案，也不能寫入 `.gsheet` 這類雲端文件捷徑 | 記成「寫入 G 失敗」；這些通常不是真正的資料 |

## 六、監控、測試與 AI 協作

| # | 症狀 | 原因 | 解法 |
|---|---|---|---|
| 42 | AI 回報「速度 0.0 MB/s」就說硬碟掛了，害使用者差點拔電源 | 讀到資料稀疏的區段時速度本來就是 0 | 看**讀到的資料量**有沒有增加；讀取位置只用來看卡在哪裡（位置也會騙人，見第 51 條） |
| 43 | 用 mapfile 的修改時間判斷卡住，結果誤判 | SMB 快取讓修改時間失真 | 看 ddrescue 自己回報的讀取量與「距上次成功讀取」 |
| 44 | 監控腳本每一輪都 SyntaxError，卻沒人發現 | 用 heredoc 現寫腳本，反斜線被吃掉（9/23 整理這個 repo 時又踩一次） | 監控和修改用的腳本寫成固定檔案，寫完先在前景跑一次、對照原始資料 |
| 45 | 以為有人在看著，其實 25%／50%／75% 的里程碑全部錯過 | 監控迴圈只寫檔不結束；AI 只有在使用者傳訊息或背景任務結束時才會被喚醒 | 監控程式**達到門檻就結束**（`狀態.py --until 75`），靠任務結束通知來觸發回報 |
| 46 | 救援進行中跑自我測試，可能清掉「需要人處理」的旗標檔（9/23 發現） | `rescue_dd.py --selftest` 把工作目錄改到暫存資料夾，但 `NEED_HELP` 是 import 時就算好的路徑，沒跟著改 | 自我測試裡一併改掉 `NEED_HELP` |
| 47 | 自我測試從 9/21 起一直失敗，commit 訊息卻寫「全部通過」（9/23 發現） | 改「空間夠就不打洞」時只跑了 `test_watchdog.py`，沒跑 `rescue_dd.py --selftest` | 自我測試強制打洞；改完程式**三個測試都要跑** |
| 48 | 用資料夾模式救完的批次，最後的 `retry` 不會補讀（9/23 發現） | 資料夾模式刻意不把批次標成「讀完」，而 `retry` 只處理讀完的批次 | `retry` 之前先對這些批次執行 `close --batch bNN` |
| 49 | 執行監控的 AI 自己改程式、自己判斷要不要重啟 | 角色沒分清楚 | 執行 AI 只負責啟動、轉述、照表處理；不改程式、不刪檔、不做判斷。指令範本見[監控AI指令範本](監控AI指令範本.md) |
| 50 | 說「115 個在安全區，這一輪會救」，結果只救回 1 個（9/24） | 「安全區」只代表讀它不會讓整顆硬碟鎖死，檔案本身仍壓在壞軌上；第一輪用 `-n` 不刮取，本來就救不到 | 「位置會不會鎖死」和「檔案有沒有壞軌」分開講、分開統計；預估一輪能救多少之前，先看那些檔案有沒有壞區 |
| 51 | 補讀在同一個卡點空轉約 6 小時，硬碟每半小時卡死一次，看門狗從沒跳過（9/24） | 兩個原因疊在一起：看門狗計時每次重啟 ddrescue 就歸零，而每輪都不滿 45 分鐘；而且用「讀取位置」判斷前進，`-A` 重啟時位置先跳回範圍開頭再回到卡點，被當成有動 | 看門狗看**讀到的資料量**（45 分鐘不滿 1 MB 就算卡住），並跨重啟累計 |
| 52 | 第一次修第 51 條，測試通過，實際跑還是空轉（9/24） | 測試假設讀取位置固定不動，沒重現紀錄裡「位置先跳回開頭」的情況 | 測試要照實際紀錄的時間線模擬；修好後先在舊版上跑，確認測試真的會失敗 |
| 53 | 補讀中途停掉後，若照正常收尾把壞區改回待處理，檔案會永遠停在待處理（9/24） | `-A` 已經把沒刮完的區塊在 mapfile 標回「沒讀過」 | 中途停掉的補讀直接 `extract --final`，不要先改狀態；動資料庫前先備份 |
| 54 | 讓 AI 用 `start_background.ps1` 啟動接續腳本，一直回報「已經在執行」，其實什麼都沒在跑（9/24 合併前測試發現） | 防止重複啟動的檢查是找命令列含腳本名稱的 bash；AI 工具的外殼命令列本身就含腳本名稱，被當成已經在跑的那一份 | 排除命令列含 `start_background` 的程式（呼叫者自己）；兩個方向都要測：沒在跑時能啟動、真的在跑時會擋下 |
