# 先判斷：該用哪一種方法

故障硬碟每多讀一次就多一分風險，方法選錯，付出的是硬碟剩下的壽命。動手前先看完這一頁。

## 第 0 步：這些事現在就停

- **不要用檔案總管打開那顆硬碟**。產生縮圖會把每張照片讀一遍。
- **不要執行 chkdsk、「掃描並修復」或任何修復工具**。它們會寫入來源碟，「修復」壞掉的目錄時還可能直接刪掉項目。
- **不用的時候把硬碟拔掉**。就算沒有程式在跑，Windows 也會在背景自己去讀它（Spot Verifier、NTFS 自動修復）。
- **硬碟有喀喀聲、刮擦聲、完全不轉，或資料非常重要又沒有任何備份**：先考慮專業資料救援。這個專案的做法只適用於「硬碟還會轉、大部分資料還讀得到」的情況。
- **先找有沒有別的備份**。這次比對兩顆舊備份碟，找到 8,093 個待救檔案（35 GB）本來就有副本，直接複製過去，省下故障碟 35 GB 的讀取量。

## 第 1 步：看症狀

| 症狀 | 代表什麼 | 用哪個方法 |
|---|---|---|
| 大部分檔案正常複製，只有少數檔案幾秒內就報錯 | 零星壞軌，硬碟本身還穩 | 方法一 |
| 讀某些檔案會卡住 1～7 分鐘才報錯 | 壞軌，Windows 在反覆重試 | 方法一可以用，但會很慢 |
| 事件檢視器出現大量 USB 或磁碟重置（UASPStor、disk 事件 153），或每十幾秒重置一次 | 硬碟會整顆卡死 | **方法二** |
| Windows 回報 MFT 或目錄損毀、資料夾打不開、照片「消失」 | 檔案目錄壞了，透過 Windows 讀不到 | **方法二**（它自己解析 MFT） |
| 讀取時整台電腦凍結或藍屏 | Windows 的儲存驅動被故障碟拖垮 | **方法二，立刻換** |

## 方法一比較簡單，沒必要就不用方法二？

對。硬碟只有零星壞軌的話，方法一就夠了，不需要架虛擬機。

| | 方法一 | 方法二 |
|---|---|---|
| 第一次準備 | 幾分鐘：裝 Python，以系統管理員執行一次 `準備硬碟.bat` | 大約半天：安裝 VMware、下載 ISO、建虛擬機、SMB 共用、SSH |
| 每次開始 | 雙擊 bat | 開虛擬機、改開機參數、打四行指令、硬碟接 USB 2.0 埠、在 VMware 按 Connect、等硬碟就緒 7～8 分鐘 |
| 需要懂的東西 | 幾乎不用 | 虛擬機、Linux 指令、ddrescue、稀疏檔 |
| 暫存空間 | 不需要 | C 槽要放得下一批 |
| 出狀況時 | 看回報照表處理 | 要分辨硬碟是卡住還是掉線、有沒有跑回 Windows |

不過方法一之所以簡單，是因為它把讀取交給 Windows。硬碟還穩的時候這很省事；硬碟開始出狀況時，這就變成風險：Windows 會在壞軌上反覆重試、重置 USB，嚴重時整台電腦一起當掉。

所以用方法一有個前提：**一邊跑一邊看換手訊號，出現任何一個就停下來，改用方法二。**

- 事件檢視器出現大量 USB 或磁碟重置，或程式回報「硬碟疑似卡死」
- Windows 回報 MFT 或目錄損毀、資料夾列不出清單
- 同一批資料夾反覆被整批延後，phase2 救壞檔一直因為硬碟卡死而停下來
- 電腦凍結或藍屏（發生一次就不要再用方法一）

**先用方法一、之後再換方法二，不會浪費。** 方法二規劃時會比對目的地，方法一已經搬好的檔案會自動跳過，不會重讀。這次就是這樣：方法一先搬出約 10 萬張照片，剩下的交給方法二。

這次的問題是換得太晚。9/15 凌晨換手訊號就出現了（USB 每 16 秒重置，同一天 Windows 回報 MFT 損毀），卻還在方法一上撐了將近兩天，當機兩次才換。

## 兩種方法比較

| | 方法一：Windows 逐檔複製 | 方法二：虛擬機 + ddrescue |
|---|---|---|
| 怎麼讀 | 透過 Windows 檔案系統，一個檔案一個檔案複製 | 在 Linux 虛擬機裡用 GNU ddrescue 直接讀磁區，Windows 端自己解析 NTFS |
| 準備工作 | 幾乎不用（Python + 一支 bat） | VMware、SystemRescue、SMB 共用、SSH |
| 碰到壞軌時 | Windows 重試 60～400 秒，程式無法中斷 | 讀不到就跳過並記下位置，全部讀完再回頭補讀 |
| 目錄壞掉的檔案 | 找不到 | 從 MFT 找得回來（找不到所屬資料夾的放進「無法判斷資料夾」） |
| 硬碟卡死時 | 整台電腦可能藍屏、凍結 | 通常只是虛擬機卡住；除非硬碟掉回 Windows（程式會偵測並叫人拔 USB） |
| 需要的暫存空間 | 不需要 | 一批的資料量（稀疏映像檔，輸出後就釋放） |
| 這次的成果 | 約 10 萬張照片 + 其他資料夾 15,350 檔 | 223,472 檔 / 1.2 TB |

## 只用方法二可以嗎？

可以，而且救得到的比兩種方法合用還多。

- **方法一救得到的，方法二都救得到。** `plan` 比對目的地時發現沒有的檔案，就會排進去讀。
- **方法二還救得到方法一救不到的。** 它自己讀 MFT，「資料夾打不開」「照片消失」的檔案都找得到。這次有一萬多個找不到所屬資料夾的檔案，就是這樣救回來的。
- 一開始就用方法二，這次可以少掉兩次當機，也不會讓 Windows 在壞軌上反覆重試。

但如果目標是「整顆硬碟」，有三種東西是任何方法都救不到，或需要另外處理的：

| 救不到的 | 原因 | 其他辦法 |
|---|---|---|
| 實體壞掉的磁區 | 磁頭讀不出來就是讀不出來。`retry` 會再試一次，但通常只能多救回一點 | 只有專業救援實驗室（開蓋換磁頭）有機會 |
| MFT 記錄本身壞掉的檔案（這次 4,138 筆） | 方法二是靠 MFT 知道檔名和資料位置，記錄壞了就不知道這個檔案存在 | 用 PhotoRec 這類「依檔案特徵掃描」的工具，在映像檔上找 JPG 等格式的開頭。照片救得回來，但沒有檔名和資料夾 |
| 刪除過的檔案殘留 | 這次決定不救 | 同上，用特徵掃描 |

另外，方法二**預設就不是讀整顆**，只讀「目的地還沒有、而且決定要救」的檔案。這次軟體、字型、音樂、電子書都跳過了，3 TB 的硬碟只讀了約 1.3 TB。要救全部檔案，把那些資料夾加進 `rescue_dd.py` 的 `OTHER_TOPS` 和 `BATCHES` 就好，不用改程式。

### 另一條路：整碟映像

也可以不分批，直接用 ddrescue 把整顆硬碟讀成一個映像檔，之後所有分析都對映像檔做，不再碰硬碟。這是專業救援常見的第一步。

| | 整碟映像 | 這次的做法（只讀需要的） |
|---|---|---|
| 讀取量 | 整顆（這次是 3 TB），包括空白區域和不需要的資料 | 只讀要救的檔案（這次約 1.3 TB） |
| 需要的空間 | 至少和硬碟一樣大 | 一批的量 |
| 之後 | 可以在映像檔上反覆分析，包括特徵掃描 | 沒讀到的區域，要再分析就得回頭讀硬碟 |
| 適合 | 硬碟還算穩、空間也夠 | 硬碟快死、空間不夠（這次 C 槽只有 931 GB，所以 9/15 決定不做整碟映像） |

最後，**硬碟本身是救不好的**。資料救完、確認目的地都上傳好之後，這顆就該退役。
