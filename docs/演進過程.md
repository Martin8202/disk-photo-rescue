# 演進過程

2026 年 9 月，一顆裝著全家二十年照片的 3 TB 外接硬碟（Seagate Expansion Desk，4K 原生磁區、NTFS）開始壞軌，而且會整顆卡死。這份文件記錄從第一天到救回 22 萬個檔案的過程：每個階段做了什麼、遇到什麼、為什麼這樣決定。

原始的規格書、交接文件與工作日誌留在私人紀錄裡，這裡是整理過的版本。個人資料已去識別化（家人A／B／C），數字與日期都是真實的。

## 第 0 階段：robocopy（9/13 以前）

一開始用 robocopy 從 `E:\照片` 搬到 Google Drive。搬到一個日本旅遊資料夾時碰到壞軌，整個卡住，使用者手動停下。這時已經搬好 28,172 張，還剩 91,672 張、約 524 GB。

盤點時發現 7 個資料夾連清單都讀不出來（錯誤 1392「檔案或目錄已損毀」）。

## 第 1 階段：方法一，Windows 逐檔複製（9/13～9/16）

### 分工

- **使用者**：所有決定（範圍、要不要繼續、硬碟拔插）。
- **Claude（Opus）**：規劃、寫規格書與程式、分析當機與紀錄。
- **執行 AI（Antigravity 裡的 Gemini）**：只負責啟動程式、每 5 分鐘轉述回報。允許清單只放行 `python`，不能自己判斷，也不能改程式。

規格書是**寫給執行 AI 看的**：每一種回報狀態代表什麼、要不要叫醒使用者、哪些事絕對不能做，都寫成表格。使用者晚上睡覺，AI 照表轉述。

### 版本演進：每一版都是被硬碟逼出來的

| 版本 | 觸發事件 | 改了什麼 |
|---|---|---|
| v3 | 9/13 初版 | 健康檔案先搬、壞檔跳過並記錄；中斷後重跑自動續傳 |
| v4 | 9/14 一張照片卡了 15 分鐘以上 | 卡住的判斷改成「多久沒讀到新資料」，大影片不會被誤判；已知壞檔清單直接不讀 |
| v5 | 9/15 硬碟退化，光是列出已搬完的資料夾就卡 6 分鐘 | 從日誌判斷已完成的資料夾，重啟時完全不碰它們 |
| v6 | 9/14 休息 5 分鐘再試，6 次都照樣失敗 | 同一資料夾連續 5 張失敗 → 剩下的整批延後。那是實體壞區，休息沒用 |
| v7 | 9/15 02:05 硬碟卡死，USB 每 16 秒重置，每個資料夾都被誤記成「讀不到」 | 連續 3 個資料夾讀不到 → 判定硬碟卡死、撤銷紀錄、停止 |
| v8 | 9/15 02:45 發現沒有程式在跑時，Windows 仍在背景讀 MFT | 關閉 Spot Verifier 與 NTFS 自動修復；加探測檔判斷硬碟還活著 |
| v9 | 9/15 程式檢查 | 目的地寫入錯誤不再當成壞軌；errno 28；不限層級的卡死偵測；「其他資料夾」模式 |
| v10 | 9/16 另一個 AI 加的功能 | 卡死時自動 `pnputil /restart-device` 重置 USB → **9/16 06:22 藍屏 0x50** |
| v11 | 9/16 藍屏之後 | 移除所有 USB 重置。單一檔案卡 10 分鐘 → 記成壞軌、由小幫手強制結束、自動重跑跳過 |

9/15 照片的 189 個資料夾全部走過一輪，G 槽累積約 10 萬張。接著開始搬「其他資料夾」（家人的個人資料、手機備份、遊戲等），到 9/16 早上搬了 15,350 檔、210 GB。

9/16 起，執行 AI 從 Gemini 換成 Claude Code 的 Sonnet（用 `/loop 5m` 每 5 分鐘轉述），開發與判斷仍由 Opus 負責。

### 走到盡頭

用方法一的 phase2 試了 3 次救壞檔，只救回 735 張，每次都在幾分鐘內因硬碟卡死停下來。這時的狀況：

- Windows 回報 MFT 損毀，有些資料夾列不出清單，有些照片「消失」了（生活照一個資料夾就少 80 張）。
- 讀到壞磁區時，Windows 會重試好幾輪，一張壞照片要卡 60～400 秒，程式無法中斷。
- 硬碟一接上，Windows 就會自己去讀它。

結論：**透過 Windows 檔案系統一張一張讀，救不到剩下的東西，還會加速硬碟死亡。**

## 第 1.5 階段：直接讀磁區的設計（9/15～9/16）

9/15 晚上規劃了 `rescue2.py`：不透過 Windows 檔案系統，把硬碟設成離線，用 Python 直接讀實體磁區、自己解析 MFT。

- 目錄索引壞了也沒關係：每個檔案的 MFT 記錄都寫著它屬於哪個資料夾、資料在哪些磁區。
- 讀失敗就把那 1 MB 標成壞區跳過，連續壞區用倍增跳躍略過。
- 照磁區位置順序讀，磁頭一路往前掃。

9/16 開發完成，自我測試用程式自己產生的迷你 NTFS 映像檔跑完整流程（包含壞磁區、MFT 壞記錄、孤兒檔、屬性清單大檔）。**但它從來沒有在真實硬碟上跑過**：還沒開始，9/16 晚上電腦就第二次當機了。

它的 NTFS 解析、檔案規劃、輸出規則後來全部被方法二沿用，現在是 `rescue_dd.py` 的函式庫。

## 轉折：兩次當機（9/16）

- **06:22 藍屏 0x50**：v10 在讀取卡住時重置 USB 裝置。
- **21:50 前後整台電腦凍結，只能硬關機**：v11 已經沒有 USB 重置了，還是凍結。

兩次都發生在 **Windows 自己的 USB 儲存驅動（UASPStor）處理壞軌**的時候。問題不在程式，在於 Windows 本身碰這顆碟就有風險，WSL2、Hyper-V 的直通底層也一樣會經過它。

使用者決定：**改用 VMware 虛擬機，讓 Linux 處理這顆硬碟，Windows 完全不碰它。**

## 第 2 階段：方法二建置（9/16 深夜～9/17）

當天晚上就完成：安裝 VMware Workstation、建立 SystemRescue 虛擬機（沒有虛擬硬碟，只開光碟）、SMB 共用資料夾、SSH 免互動連線。建環境的 bat 第一次執行就失敗了（LF 換行＋中文檔名，cmd 把每一行切碎，一個指令都沒執行到），改成純 ASCII + CRLF 才成功。

**不接真的硬碟先演練**：在虛擬機裡用 device-mapper 做一顆 1.1 TB 的假硬碟，放幾段真資料和一段會讀取失敗的區域，驗證：
- 透過 SMB 寫稀疏映像檔，沒讀的位置不會真的佔空間（邏輯 1.1 TB，實際 24 MB）
- ddrescue 只讀指定範圍，讀到的資料 SHA256 一致，壞區正確標記

演練中發現 ddrescue 1.30 的行為：搭配 `--domain-mapfile` 時 `-c 256` 會漏讀整段好資料，補讀一定要加 `-A`。

9/17 凌晨接上真的硬碟，連續踩了幾個坑：
- `usb.autoConnect` 讓硬碟連線兩次、掉回 Windows，又開始每 16 秒重置。
- vmx 殘留的 USB 集線器項目讓虛擬機開機幾分鐘後整個凍結。
- 硬碟通電後要 7 分鐘才就緒，Linux 30 秒就放棄了。

都解決後，9/17 上午讀出 MFT：2,069 MB 讀到 2,052 MB，壞區 16.5 MB，共 50 萬筆記錄。

## 第 3 階段：分批救援（9/17～9/19）

### 範圍由使用者決定

`plan` 從 MFT 建出清單後，使用者看過報告縮小範圍：
- 軟體、字型、音樂、電子書不救（可以重新取得）。
- 只救 G 槽真的沒有的。
- 找不到所屬資料夾的孤兒檔要救。
- 看過孤兒檔分析後，手機垃圾桶裡的照片和一批 CD 音樂（4,158 檔）不救。

最後是 13 批、1,269 GB。遊戲那批排在最後，輪到時要先問使用者。

### 為什麼要分批

當初預估要暫存 1.8 TB，C 槽只有 931 GB。所以設計成：讀完一批就輸出到 G 槽，然後在映像檔上打洞，把空間還給 C 槽。

### 執行

- **b01**（照片、手機備份）9/17 14:30～16:36：救回 15,001 檔，最後 307 MB 是密集壞軌，一直卡，用 `close` 收尾留給最後補讀。
- **b02**：20,833 檔。
- 9/17 23:42 使用者說：之後不用每批都等他確認，一批接一批自動跑，回報改成每 20 分鐘。於是寫了自動接續腳本：每一批都要正常結束才接下一批，任何異常就整個停下來。
- 9/18～9/19 自動跑完 b03～b10，其中 b04、b06、b07 完全沒有壞軌。

## 第 4 階段：硬碟開始頻繁死亡（9/19～9/20）

- **9/19 23:49**：b11 讀到 52% 時，硬碟從虛擬機掉回 Windows。同一時段 Windows 記錄 1,169 筆映像檔「延遲寫入失敗」。查證後沒有檔案受損（那段資料還沒輸出），但學到一件事：**只有輸出到 G 槽的資料才算數**。之後每批開始前，都會把「mapfile 說讀到了但還沒輸出」的區段改回未讀重讀。
- **9/20** b11 一天失敗四次。其中一次整顆鎖死，卡了 2.5 小時，ddrescue 自己的 10 分鐘逾時完全沒反應（程式被凍在核心的 I/O 等待裡）。

補強了三件事：
1. **看門狗放在虛擬機外面**：看 mapfile 的讀取位置有沒有前進。
2. **分清兩種故障**：硬碟還在只是卡住 → 等，最多 45 分鐘（實測常常 3～8 分鐘就自己恢復）；硬碟從匯流排掉了 → 立刻停下來叫人，繼續探測沒有意義。
3. **危險區**：卡太久的位置前後各 5 GB 記下來，之後每一批都跳過，留到最後補讀。讀取順序改成**離危險區越遠的先讀**（b12 排到 b11 前面），硬碟剩下的壽命先花在最安全的資料上。

同一天，程式從 Google Drive 搬到本機的 git repo（也就是這個 repo 的前身）。原因是雲端同步可能在執行中覆寫程式，而且改完還要手動複製，版本容易不一致。

## 第 5 階段：系統層的問題（9/20～9/21）

硬碟以外的問題開始浮現：

- **延遲寫入失敗一天 11,885 次，記憶體被髒頁吃掉 13.5 GB**。查了一整晚，真正的原因是 NTFS 片段上限：一直在稀疏映像檔上打洞，檔案被切成 193 萬個片段，撞上 NTFS 的上限後所有寫入都失敗。打洞本身沒有錯（原始規模不打洞一定爆），錯在無條件執行：只剩 270 GB 要救、C 槽還有 489 GB 時，根本不需要打。改成空間不夠才打，並把映像檔刪掉重建。
- **SMB 掛載改 `cache=none`**，虛擬機記憶體從 4 GB 降到 1.5 GB（實測只用 379 MB）。
- **USB 2.0 的發現**：硬碟接在 USB 3.0 埠時 Linux 用 UAS 驅動，這顆碟在 UAS 下完全讀不到；換到 USB 2.0 埠就正常。
- **`amd64_edac` 模組**在 VMware 裡崩潰，讓 `/dev/disk/by-id/` 永遠不出現。開機參數擋掉它就好了。
- **映像檔被刪掉後，ddrescue 自己建了一個非稀疏檔**，半小時吃掉 511 GB。之後每次 `copy` 前都先檢查。

### 資料夾模式與「不用讀的就不要讀」

硬碟已經衰弱到整批 100 GB 讀不完，於是加了 `copy --folder`：一次只救一個資料夾，讀完一個就有一個確定的成果。

同時想辦法減少要從故障碟讀的量：
- **比對重複**：找出其他資料夾已經有同一個檔案的（檔名＋大小＋修改時間相同），使用者同意後標記不讀，省下 4,943 檔、8.5 GB。
- **找舊備份**：比對兩顆舊備份碟，8,093 檔、35 GB 本來就有備份，直接複製過去。
- 試過在硬碟掉回 Windows 時直接從 Windows 複製，每個檔案都回報 `Invalid argument`，放棄。

9/21 凌晨的狀態：已救回 207,328 檔，還剩 16,713 檔、270 GB。

## 第 6 階段：最後幾批（9/21～9/23）

- 9/21～9/22 清晨：照資料夾模式把剩下的照片、影片、文件跑完。
- 9/22 05:15～14:34：錄音資料夾 104.5 GB，零壞軌。
- 9/22 14:36 開始跑遊戲（使用者說可以最後再救）。23:58 程式碰到偶發的寫入錯誤當掉。
- 9/23 04:10 寫了會自動重試的接續腳本，遊戲讀到 99.8%。

## 第 7 階段：補讀與結束（9/23～9/24）

- 9/23 21:52 最後一輪：剩 140 個個人檔案，其中 25 個在危險區先不讀，其餘 115 個用資料夾模式跑。9/24 10:59 跑完，**只救回 1 個**。那 115 個雖然不在危險區，但每個都壓在壞軌上，第一輪不刮取的讀法本來就救不到。事前把「不在危險區」說成「這一輪會救」是錯的（[踩過的坑](踩過的坑.md)第 50 條）。
- 9/24 12:57 補讀，使用者決定分兩段：先補讀危險區以外，危險區最後、要再問他。為此加了 `retry --zones`。
- 補讀卡在同一個位置：每半小時「讀到卡點 → 硬碟卡死 → ddrescue 結束 → 重啟」一次，看門狗從沒跳過。17:09 停下修正、17:17 重跑，到 20:38 還是卡在同一點——第一次的修正只解決了計時歸零，沒發現重啟時讀取位置會先跳回開頭（第 51、52 條）。兩次共 7.5 小時，只多讀出約 0.5 MB。
- 20:38 使用者決定停損：停止補讀，直接 `extract --final`。140 個檔最後 6 張照片存成部分損壞（壞區 0.1～4.6%），114 個壞區太多沒存（壞區比例中位數 79%），19 個在危險區沒讀。使用者決定不送專業救援。
- 之後把看門狗改成看讀到的資料量並跨重啟累計，用照實際紀錄模擬的測試確認（舊做法在這個測試上會失敗）。這個版本沒有再在真實硬碟上跑過。

## 回頭看

1. **方法換得太晚**。第一次出現 USB 反覆重置、MFT 損毀時，就該直接改用虛擬機，不該在 Windows 上多撐兩天、當機兩次。方法一不是沒用（它三天搬出了 10 萬張），但它應該只用在硬碟還穩的時候。
2. **「讀到了」不等於「救到了」**。mapfile、資料庫、映像檔都可能跟實際寫到目的地的內容不一致。只有輸出到目的地、驗證過的才算數。
3. **能不讀就不讀**。先找備份、先比對重複、先救 MFT。故障碟的每一次讀取都是消耗品。
4. **自動化一定要會叫人**。自動接續腳本出事就停；程式需要人的時候寫一個旗標檔，把原因和該做的步驟寫清楚；監控程式達到門檻就結束，才叫得醒 AI。
5. **人負責判斷，AI 負責執行**。範圍、優先順序、什麼不救、什麼時候可以自動跑，全部由使用者決定；執行 AI 只照規格書轉述，不自己判斷。規格書寫給 AI 讀，每種狀態該怎麼處理都寫成表格。
6. **錯誤要變成規則**。同樣的錯（heredoc 吃掉反斜線、bat 編碼、監控不會叫人）犯了第二次，就寫進規則或記憶，不只在對話裡說一句。整理這個 repo 時又發現三個問題（自我測試會清掉旗標檔、自我測試兩天來一直失敗、資料夾模式的批次不會被補讀），也都收進[踩過的坑](踩過的坑.md)。
7. **知道什麼時候該停**。最後 133 個檔花了一整天，只多存出 6 張部分損壞的照片，還讓硬碟反覆卡死。補讀要先設停損點，看讀到的資料量決定要不要繼續，而不是看它「還在跑」。
